## F11 Hono Node의 Promise와 동기 IO 경계

공식 생성 명령은 `npm create hono@0.19.5 -- -t nodejs -i -p npm hono-node`였다. Hono 4.13.9, `@hono/node-server` 2.1.1, TypeScript 7.0.2, Oxlint 1.85.0, `oxlint-tsgolint` 7.0.2003을 설치했다. 두 규칙만 켠 임시 `oxlint.f11.json`은 아래와 같다.

```json
{
  "plugins": ["typescript", "node"],
  "categories": { "correctness": "off" },
  "options": { "typeAware": true },
  "rules": {
    "typescript/no-floating-promises": ["error", { "ignoreVoid": true, "checkThenables": false, "ignoreIIFE": false }],
    "node/no-sync": ["error", { "allowAtRootLevel": true, "ignores": [] }]
  }
}
```

`src/index.ts`는 Hono의 typed `Variables`와 `app.use('*', async (c, next) => { c.set('requestId', 'f11'); await next() })`, 비동기 `/api/me` 라우트를 사용했다. `npm run build`는 exit 0, 빌드한 Node 서버의 `GET /api/me`는 HTTP 200과 `{"requestId":"f11"}`을 반환했다. 규칙별 fixture는 다음과 같이 **서로 다른 파일**로 실행했다.

```ts
// src/valid.ts — 정상 middleware와 최상위 시작 설정 읽기
import { readFileSync } from 'node:fs'
import { Hono } from 'hono'

const startupContents = readFileSync(new URL('../package.json', import.meta.url), 'utf8')
const writeAudit = async (_value: string): Promise<void> => { await Promise.resolve() }
const app = new Hono()
app.use('*', async (_c, next) => {
  await writeAudit('start')
  await next()
})
app.get('/valid', async (c) => {
  await writeAudit('route')
  return c.text(String(startupContents.length))
})
export { app }
```

```ts
// src/floating.ts — 미처리 Promise
import { Hono } from 'hono'

const writeAudit = async (): Promise<void> => { await Promise.resolve() }
const app = new Hono()
app.use('*', async (_c, next) => {
  writeAudit()
  await next()
})
export { app }
```

```ts
// src/sync-hot.ts — 요청 경로 동기 I/O
import { readFileSync } from 'node:fs'
import { Hono } from 'hono'

const app = new Hono()
app.get('/hot', (c) => c.text(readFileSync('config.json', 'utf8')))
export { app }
```

```ts
// src/sync-startup-function.ts — 앱 시작 시 한 번 호출할 수 있는 함수
import { readFileSync } from 'node:fs'

export function loadStartupConfig(): string {
  return readFileSync('config.json', 'utf8')
}
```

각 `src/<file>.ts`에 `node_modules/.bin/oxlint -c oxlint.f11.json -f json src/<file>.ts`를 실행했다. 정상 typed middleware와 top-level sync는 0진단·exit 0이다. `writeAudit()`의 미처리 Promise는 `typescript(no-floating-promises)` error 한 건·exit 1, 요청 경로의 `readFileSync`는 `node(no-sync)` error 한 건·exit 1이었다. **시작 로딩 함수의 `readFileSync`도 같은 error·exit 1**이다. 이 함수는 빌드한 JS를 Node에서 직접 호출했을 때 `{"mode":"startup"}`을 출력하고 exit 0이었다. 따라서 함수 내부 sync I/O를 일괄 금지하면 실행 가능한 정상 시작 코드를 막는다.

옵션별 재실행도 했다. `allowAtRootLevel:false`는 top-level sync에 error 한 건을 추가했다. `ignores:['readFileSync']`는 요청 처리의 위반까지 0진단으로 만들었다. `ignoreVoid:true`에서 `void writeAudit()`는 0진단, `false`에서는 `typescript(no-floating-promises)` error 한 건이며 `void writeAudit().catch(...)`는 두 설정 모두 0진단이었다. `typeAware:false`에서는 floating fixture의 활성 규칙 수가 **0**, 진단 0·exit 0이었다. 규칙 이름만 설정해 타입 기반 검사 활성화를 보장할 수 없다. [Oxc type-aware 요구](https://oxc.rs/docs/guide/usage/linter/type-aware)대로 TS7+와 별도 `oxlint-tsgolint` 설치를 전제로 한 선택 경로에만 이 규칙을 둔다. `node/no-sync`는 공통 차단에서 제외하고 프로젝트가 실제 요청 경로를 특정할 때에만 다시 검토한다.

## F12 Hono Workers의 AsyncLocalStorage

`npm create hono@0.19.5 f12-worker -- --template cloudflare-workers --install --pm npm`으로 공식 템플릿을 생성하고 Hono 4.13.9, Wrangler 4.142.0, TypeScript 7.0.2, `@types/node` 24.19.0으로 고정했다. `wrangler.jsonc`에 `compatibility_date:"2026-08-03"`과 `compatibility_flags:["nodejs_compat"]`를 설정했다. 생성한 `worker-configuration.d.ts`에서 workerd 타입 버전은 1.20260926.1이었다.

```jsonc
// wrangler.jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "oxc-f12-hono-als-probe",
  "main": "src/index.ts",
  "compatibility_date": "2026-08-03",
  "compatibility_flags": ["nodejs_compat"]
}
```

TypeScript 설정은 `target:"ESNext"`, `module:"ESNext"`, `moduleResolution:"Bundler"`, `strict:true`, `skipLibCheck:true`, `types:["node"]`, `lib:["ESNext"]`, `jsx:"react-jsx"`, `jsxImportSource:"hono/jsx"`였다.

```ts
import { AsyncLocalStorage } from 'node:async_hooks'
import { Hono } from 'hono'

const requestContext = new AsyncLocalStorage<{ requestId: string }>()
const app = new Hono()

app.use('*', async (c, next) => {
  const requestId = c.req.query('id') ?? 'missing'
  return requestContext.run({ requestId }, async () => {
    await next()
    c.header('x-als-after-next', requestContext.getStore()?.requestId ?? 'missing')
  })
})

app.get('/', async (c) => {
  const before = requestContext.getStore()?.requestId ?? 'missing'
  await new Promise<void>((resolve) => setTimeout(resolve, 5))
  const after = requestContext.getStore()?.requestId ?? 'missing'
  return c.json({ before, after })
})

export default app
```

```sh
npx wrangler types --env-interface CloudflareBindings
npx tsc --noEmit
npx wrangler deploy --dry-run --outdir dist-f12
npx wrangler dev --local --ip 127.0.0.1 --port 18787
curl -i 'http://127.0.0.1:18787/?id=alpha'
```

타입 생성, `tsc`, dry-run은 모두 exit 0이었다. 로컬 HTTP는 200, `x-als-after-next: alpha`, `{"before":"alpha","after":"alpha"}`이었다. 서로 다른 `request-0`부터 `request-19`까지 **20개 동시 fetch**에서 status 200, header ID, 응답 JSON의 `before`·`after` ID를 `node:assert/strict`로 비교했고 모두 일치하며 exit 0이었다. 타입 검사에는 `types:["node"]`와 `@types/node`를 사용했다. [Cloudflare Node 호환 안내](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)와 [AsyncLocalStorage 지원 범위](https://developers.cloudflare.com/workers/runtime-apis/nodejs/asynclocalstorage/)를 함께 봐야 한다. 이 실험은 `run()`·`getStore()`의 **로컬 런타임 경로**만 확인한다. 전체 Node API, 원격 Cloudflare 배포, 다른 compatibility date는 `not_run`이다.

동시 요청 검증은 다음 스크립트를 `wrangler dev` 실행 중 별도 Node 프로세스에서 돌렸다.

```js
import assert from 'node:assert/strict'

const responses = await Promise.all(
  Array.from({ length: 20 }, (_, i) => {
    const id = `request-${i}`
    return fetch(`http://127.0.0.1:18787/?id=${id}`).then(async (response) => ({
      id,
      status: response.status,
      header: response.headers.get('x-als-after-next'),
      body: await response.json(),
    }))
  }),
)
for (const result of responses) {
  assert.equal(result.status, 200)
  assert.equal(result.header, result.id)
  assert.deepEqual(result.body, { before: result.id, after: result.id })
}
```

## F13 Next App Router의 beforeInteractive

Oxlint 1.85.0에서 다음 최소 설정을 사용했다. 동일한 `next/script`의 `<Script src="/consent.js" strategy="beforeInteractive" />`를 root `app/layout.tsx`(허용), `app/page.tsx`와 `app/dashboard/layout.tsx`(배치 위반)에 넣었다. `src/app/` 배치와 root `app/` 배치를 모두 시험했다.

```json
{
  "plugins": ["nextjs"],
  "categories": { "correctness": "off" },
  "rules": { "nextjs/no-before-interactive-script-outside-document": "warn" }
}
```

```tsx
// src/app/page.tsx; app/page.tsx와 pages/index.tsx에도 동일한 본문 사용
import Script from 'next/script'
export default function HomePage() {
  return <main><Script src="/consent.js" strategy="beforeInteractive" />Home</main>
}
```

정상 root `layout.tsx`는 `<html lang="en"><body>{children}<Script src="/consent.js" strategy="beforeInteractive" /></body></html>`을 반환했다. 위반 중첩 `dashboard/layout.tsx`는 `<section><Script src="/consent.js" strategy="beforeInteractive" />{children}</section>`을 반환했다. `dashboard/page.tsx`에는 정상 `afterInteractive` Script를 사용했다. Pages 대조의 `_document.tsx`는 root layout 본문을 경로만 바꾼 fixture다.

```sh
node_modules/.bin/oxlint --config .oxlintrc.json --format=json src/app/page.tsx
node_modules/.bin/oxlint --config .oxlintrc.json --deny-warnings --format=json pages/index.tsx
```

| 파일 | Oxlint 진단 / exit | `--deny-warnings`의 exit |
| --- | --- | --- |
| `src/app/layout.tsx` 또는 `app/layout.tsx` | 0 / 0 | 0 |
| `src/app/page.tsx` 또는 `app/page.tsx` | 0 / 0 | 0 |
| `src/app/dashboard/layout.tsx` 또는 `app/dashboard/layout.tsx` | 0 / 0 | 0 |
| 대조 `pages/index.tsx` | `next(no-before-interactive-script-outside-document)` warn 1 / 0 | 1 |
| 대조 `pages/_document.tsx` | 0 / 0 | 0 |

Pages의 위반은 severity `error`로 변경하면 exit 1이고 `--fix` 뒤에도 파일과 진단이 그대로였다. App 배치 위반은 severity를 바꿔도 진단 0이다. 이 동작은 [Oxlint 1.85.0 해당 규칙 소스](https://github.com/oxc-project/oxc/blob/6060eee768ef4cc3876eda2cbf54cd9bf5c5acad/crates/oxc_linter/src/rules/nextjs/no_before_interactive_script_outside_document.rs#L94-L96)와 [Next 원 규칙 소스](https://github.com/vercel/next.js/blob/canary/packages/eslint-plugin-next/src/rules/no-before-interactive-script-outside-document.ts#L30-L35)의 App 경로 early return과 일치한다. [Next의 Script 문서](https://nextjs.org/docs/app/api-reference/components/script)는 App Router의 `beforeInteractive`를 root layout에 두도록 안내한다.

Next 16.3.6, React 19.2.8, TS5.9.3을 설치한 **최소 App Router 앱**에 같은 잘못된 page·nested layout 파일과 `public/consent.js`, `public/analytics.js`를 넣었다. `next.config.mjs`를 `export default {}`와 `export default { output: 'export' }`로 각각 설정하고 `NEXT_TELEMETRY_DISABLED=1 npm run build`를 실행했으며 둘 다 exit 0이었다. 정적 출력은 `out/index.html`과 `out/dashboard.html`을 생성했다. **빌드 통과가 이 배치 계약을 검증하지 않는다.** App Router 후보에서 이 규칙을 제거하고, root layout에만 둔다는 계약을 별도 검사로 강제할지는 범위·정확도·유지 비용을 비교한 뒤 결정한다. Pages Router용으로는 유효한 진단이지만 현재 패키지의 Next 범위 밖이다.

## F13a 별도 beforeInteractive 배치 검사 후보

[Next Script 문서](https://nextjs.org/docs/app/api-reference/components/script)는 `beforeInteractive`를 root layout에 두라고 한다. [layout 규약](https://nextjs.org/docs/app/api-reference/file-conventions/layout)의 root layout은 `app/layout.tsx`만이 아니다. 상위 layout이 없다면 `app/(shop)/layout.tsx`, `app/dashboard/layout.tsx`, `app/[lang]/layout.tsx`도 root일 수 있다. 따라서 `app/layout` 경로만 허용하는 단순 금지는 정상 패턴을 막는다.

Oxlint 1.85.0의 [JS plugin 기능](https://oxc.rs/docs/guide/usage/linter/js-plugins)으로 **임시 규칙**을 만들었다. `next/script`의 default import 바인딩을 별칭까지 찾고, JSX 태그가 그 ImportBinding을 실제 참조하는지 scope에서 확인했다. `strategy="beforeInteractive"` 또는 같은 문자열 JSX expression을 확인한 뒤, App Router 파일의 상위 디렉터리에 `layout.{js,jsx,ts,tsx}`가 있는지로 현재 `layout`이 root인지 판정했다. 임시 설정은 `plugins:[]`, `jsPlugins:["./plugin.mjs"]`, `categories.correctness:"off"`, `next-script-contract/root-before-interactive:"error"` 한 규칙이었다.

실험용 `plugin.mjs`의 전체 소스는 다음과 같다. **배포할 규칙의 초안이 아니며** 아래의 경로 추론 결함을 수리하지 않고 복사해서 쓰면 안 된다.

```js
import { existsSync } from 'node:fs'
import { basename, dirname, join, sep } from 'node:path'

const layoutExtensions = ['js', 'jsx', 'ts', 'tsx']
const hasLayout = (dir) => layoutExtensions.some((ext) => existsSync(join(dir, `layout.${ext}`)))

function isRootLayout(filename) {
  if (!/^layout\.(?:js|jsx|ts|tsx)$/.test(basename(filename))) return false
  const parts = filename.split(sep)
  const appIndex = parts.lastIndexOf('app')
  if (appIndex < 0) return false
  const appDir = parts.slice(0, appIndex + 1).join(sep) || sep
  let parent = dirname(dirname(filename))
  while (parent.startsWith(appDir) && parent !== dirname(appDir)) {
    if (hasLayout(parent)) return false
    if (parent === appDir) break
    parent = dirname(parent)
  }
  return true
}

const rule = {
  meta: {
    type: 'problem',
    docs: { description: 'Place direct beforeInteractive next/script elements in an App Router root layout' },
    messages: { wrongPlace: 'Direct beforeInteractive next/script usage belongs in an App Router root layout.' },
    schema: [],
  },
  create(context) {
    const scriptLocals = new Set()
    const filename = context.filename
    const insideApp = filename.split(sep).includes('app')
    if (!insideApp || isRootLayout(filename)) return {}

    return {
      ImportDeclaration(node) {
        if (node.source.value !== 'next/script') return
        for (const specifier of node.specifiers) {
          if (specifier.type === 'ImportDefaultSpecifier') scriptLocals.add(specifier.local.name)
        }
      },
      JSXOpeningElement(node) {
        if (node.name.type !== 'JSXIdentifier' || !scriptLocals.has(node.name.name)) return
        let scope = context.sourceCode.getScope(node)
        let binding
        while (scope && !binding) {
          binding = scope.set.get(node.name.name)
          scope = scope.upper
        }
        if (!binding?.defs?.some((definition) => definition.type === 'ImportBinding' && definition.node?.type === 'ImportDefaultSpecifier')) return
        const strategy = node.attributes.find((a) =>
          a.type === 'JSXAttribute' && a.name.name === 'strategy'
        )
        const value = strategy?.value
        const literal = value?.type === 'Literal'
          ? value.value
          : value?.type === 'JSXExpressionContainer' && value.expression?.type === 'Literal'
            ? value.expression.value
            : undefined
        if (literal === 'beforeInteractive') {
          context.report({ node, messageId: 'wrongPlace' })
        }
      },
    }
  },
}

export default {
  meta: { name: 'next-script-contract' },
  rules: { 'root-before-interactive': rule },
}
```

```json
  "rules": { "next-script-contract/root-before-interactive": "error" }
}
```

## F14 Next src 경로

Oxlint 1.85.0의 로컬 최소 설정으로 `react/jsx-key`, `react/rules-of-hooks`, `jsx-a11y/alt-text`, `nextjs/no-sync-scripts` 네 ID만 error로 켰다. 원래 React 좁은 글롭 세 가지는 `src/app/**/*.{ts,tsx,js,jsx}`, `src/features/**/*.{ts,tsx,js,jsx}`, `src/shared/**/*.{ts,tsx,js,jsx}`였고, JSX·Next 글롭은 각각 `src/**/*.{tsx,jsx}`와 `src/**/*.{ts,tsx,js,jsx}`였다. 로컬 `react(files)`, `jsxA11y(files)`, `nextjs(files)` 함수는 각각 `categories:{correctness:'off'}`와 `{overrides:[{files,plugins:[해당 plugin],rules:{해당 최소 규칙}}]}`를 반환했고, 소비자 `oxlint.config.mts`가 `defineConfig({extends:[react(reactFiles),jsxA11y(jsxFiles),nextjs(nextFiles)],ignorePatterns:['.next/**','out/**','src/app/generated/**']})`로 합쳤다. 이것은 **네 규칙의 소형 함수**이고 제안한 공개 패키지 API는 아니다.

`src/app/(shop)/cart/_components/CartSummary.tsx`, `src/features/cart/ui/CartView.tsx`, `src/shared/ui/SharedBanner.tsx` 각각의 key 없는 map, alt 없는 img, 동기 script는 `react(jsx-key)`·`jsx-a11y(alt-text)`·`next(no-sync-scripts)` **세 error·exit 1**을 냈다. 실제 위반 JSX의 핵심은 `<>{items.map(item => <span>{item}</span>)}<img src="/sku.png" /><script src="/legacy.js" /></>`다. 정상 JSX는 `key={item}`, `alt="Product SKU"`, `async`를 넣었고 진단 0·exit 0이었다. 조건부 `if (condition) useState(0)`이 있는 `src/features/cart/model/useCart.ts`와 route-local `src/app/(shop)/cart/_lib/useRouteCart.ts`는 `react-hooks(rules-of-hooks)` error·exit 1, unconditional Hook은 0이었다. 명령은 임시 프로젝트 루트에서 `node node_modules/oxlint/bin/oxlint -c oxlint.config.mts -f json '<fixture>'` 형태로 실행했다.

React 글롭을 좁게 두었을 때 `src/server/ServerWidget.tsx`의 JSX key와 `src/server/useServer.ts`의 조건부 Hook은 누락됐으나 JSX a11y·Next 규칙은 적용됐다. 후속 설정에서 `react(['src/**/*.{ts,tsx,js,jsx}'])`로 넓히자 `src/server/ServerView.tsx`의 key 누락과 `src/server/useServer.ts`의 조건부 Hook을 각각 error로 검출했다. 정상 `ServerViewGood.tsx`와 `src/server/readConfig.ts`의 `node:fs/promises` 사용은 0진단이었다. 후속 좁은 설정에서는 같은 server 위반 둘 다 0진단이었다. 이 후속에는 **두 React 규칙만** 켰고, 전체 19개 결과는 F14a에 따로 기록한다.

루트 `app/`를 쓰는 소비자는 React·JSX·Next 세 글롭을 모두 root 경로로 바꿔야 같은 진단을 얻었다. `.next/`, `out/`, `src/app/generated/`는 ignore 후 검사 대상에서 빠졌다. 무시된 단일 파일을 직접 지정하면 `No files found to lint`로 exit 1일 수 있어 CI는 안정적인 디렉터리를 대상으로 둔다. **이 F14 소형 실험에는 네 규칙만 켰다.** 전체 React 19개는 다음 F14a에서 별도로 시험했고, 공개 `react({ files })`·`jsxA11y({ files })`·`nextjs({ files })` builder 및 74개 전체 합성은 구현·실행하지 않았다.

[기존 TS6/TS7 호환 실험](starter-verification-2026-09-28.md#타입-기반-검사와-metadata)은 별도 조합 결과다.
